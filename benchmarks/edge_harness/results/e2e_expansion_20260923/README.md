# 2026-09-23 WSL CPU and native Windows expansion

This extends the [60-cell device × model matrix](../e2e_profiling_20260922/evidence/summary/README.md) with previously unrun WSL CPU and native Windows paths. The September 22 timing tables remain historical. MiniCPM-o now has separate 20-request serial text-to-speech timing runs on WSL CPU and native Windows GPU, plus one synthetic image and one synthetic audio input on each platform. A separate pinned GGUF route ran combined image+audio to text+speech requests on WSL CPU, native Windows CPU and native Windows Radeon 890M+CPU. The two Windows routes answered one spoken red-square question correctly with matching language token IDs; those C++ routes now also pass a bounded complete request through [Omni whole-session stages](evidence/minicpmo_omni_cpp/README.md), with broader input-grounded quality unqualified. The earlier direct InternVLA timings were single observations. Spark has a 20-request Omni output-head component profile on the HX370 AMD NPU and separate 20-request **complete text** profiles through standalone llama.cpp on native Windows CPU and Radeon 890M. The latter now also run as bounded whole-session Omni stages, with public AsyncOmni requests checked separately. Qwen3-TTS has separate 20-request standalone and bounded Omni whole-session text-to-WAV profiles on native Windows CPU; the CPU+Radeon 890M hybrid route likewise has standalone and Omni profiles. None is a sustained or full-modality profile. The [checkpoint manifests](../e2e_recovery_20260923/README.md) pin the earlier real weights; the [Spark NPU component record](evidence/spark_amd_npu_output_head/README.md), [standalone CPU/Radeon whole-model record](evidence/spark_radeon890m_llamacpp/README.md), [Omni CPU/Radeon whole-session record](evidence/spark_omni_llamacpp/README.md), [standalone CPU Qwen TTS record](evidence/qwen_tts_native_cpu/README.md), [Omni CPU Qwen TTS record](evidence/qwen_tts_omni_cpu/README.md), [standalone joint CPU+Radeon TTS record](evidence/qwen_tts_radeon890m_joint/README.md), and [Omni joint TTS record](evidence/qwen_tts_omni_hybrid/README.md) pin their respective artifacts. No model, precision or context was silently substituted.

InternVLA also has a separate [admitted Omni whole-policy synthetic profile](evidence/internvla_omni_policy/README.md) on WSL CPU and WSL CPU+Radeon 890M: one warmup plus 20 serial complete requests per placement, explicit 16 GiB shared-RAM reservation, pre-launch refusal, hybrid in-flight abort, and a public `AsyncOmni.generate` action output. The two complete-request profiles are 3.175/3.219 s CPU and 3.120/3.197 s hybrid p50/p95; they use a patterned fixture distinct from the older direct hybrid run. Action relative L2 difference is 2.305% without a task tolerance. This advances integration depth only; robot-task E2E remains unqualified.

The [WSL RTX 5090 Laptop Omni CUDA policy profile](evidence/internvla_omni_cuda/README.md) used the same real Place_Markpen checkpoint and patterned fixture with the BF16 policy and Cosmos encoder resident on CUDA. One warmup plus 20/20 serial terminal action requests had complete-request wall p50/p95 0.382/0.399 s, excluding 43.82 s startup. A 16 GiB host/16 GiB VRAM reservation admitted the route, an 8 GiB VRAM demand was refused before worker launch, and an in-flight abort cleared both ledgers. The public action entrypoint passed. Relative to the separate WSL CPU output, action relative L2 difference was 2.006% without a task tolerance. This is synthetic policy integration, not physical robot-task qualification or a comparison with the earlier zero-input direct CUDA forward.

The [native Windows RTX 5090 Laptop Omni CUDA policy profile](evidence/internvla_omni_windows_cuda/README.md) separately ran the same patterned fixture and real checkpoint. One warmup plus 20/20 serial terminal action requests had complete-request wall p50/p95 0.746/0.806 s, excluding 147.77 s startup that included loading weights from a WSL UNC path. A 16 GiB host/16 GiB VRAM reservation, 8 GiB VRAM pre-launch refusal, in-flight abort, and public action entrypoint passed. Relative L2 was 2.340% versus its separate native CPU output and 1.555% versus the WSL CUDA action chunk; there is no task tolerance. These OS runs are not a paired speed comparison or robot-task qualification.

For the AMD NPU route, the [real InternVLA Cosmos encoder export](evidence/internvla_cosmos_amd_npu/README.md) matched its source on two fixed inputs under ORT CPU (relative L2 below 2.3e-6). Conv+MatMul A16W8 QDQ failed a 0.1% numerical gate by a wide margin and its VitisAI compilation emitted a missing-scale fatal assertion. MatMul-only A16W8 retained CPU parity but both original and preprocessed candidates hit a separate compiler assertion. No NPU node executed and no full policy ran on that placement. These are artifact-specific failures, not a model-wide or hardware-wide rejection.

A further [native Windows CPU Omni policy profile](evidence/internvla_omni_windows_cpu/README.md) ran the same patterned synthetic fixture with the real Place_Markpen checkpoint: one warmup plus 20/20 identical finite action chunks, nearest-rank complete-request wall p50/p95 4.878/4.902 s, and 135.60 s startup. The public action entrypoint, pre-launch 8 GiB refusal and in-flight abort passed with a 16 GiB host-RAM reservation and zero ledger residue. The native action chunk differed from the WSL CPU output by 2.1795% relative L2; no robot-task tolerance exists. The earlier one-forward native CPU result used a zero-input fixture and must not be compared as the same profile.

The matching [native Windows CPU+Radeon Omni policy profile](evidence/internvla_omni_windows_hybrid/README.md) kept the BF16 action policy on CPU and ran only the pinned FP32 six-frame Cosmos encoder through a native DirectML worker. It returned 20/20 identical finite action chunks after one warmup at nearest-rank complete-request wall p50/p95 4.575/4.725 s, versus the separate native CPU baseline 4.878/4.902 s; startup was 140.31 s versus 135.60 s. Hybrid-vs-CPU action relative L2 difference was 2.4391% without a task tolerance. Native hybrid pre-launch refusal, in-flight abort and public `AsyncOmni.generate` action output passed with a 16 GiB shared-RAM reservation. The output device was verified as Radeon 890M, not every internal graph op. This is a synthetic integration pass, not robot-task E2E or sustained benefit.

A later [native Windows Radeon MiniCPM-o Omni profile](evidence/minicpmo_omni_radeon_profile20/README.md) completed one warmup and 20 serial **combined spoken-question+image → text+speech** requests with the same pinned GGUF set and patched C++ CLI. All 20 answered the red-square question and emitted complete speech; the first measured WAV independently transcribed with WER 0 using pinned Whisper tiny.en. Nearest-rank complete-request wall p50/p95 was **87.27/91.45 s**, much slower than the earlier 18.27 s single cold Omni request. A separate cold rerun after the profile took 88.01 s. All 21 successful new worker logs report Radeon Vulkan0 37/37 language layers, CPU Token2Wav and repeated `PrefetchVirtualMemory` warnings. The 21 GiB shared-RAM budget fit the pre-load available-RAM check and cancellation released it. A later one-request CPU-only control with the same fixture took 73.63 s and also logged prefetch warnings despite 32.28 GB OS-available before load. The CPU control was not a matched-condition comparison; no full memory/power trace identifies the regression's cause. This advances repeated functional evidence while weakening any claim of predictable Radeon performance under current memory conditions.

The [native-storage follow-up](evidence/minicpmo_omni_native_weights_io/README.md) used the same ten hashed GGUF weights copied to Windows NTFS. Native Windows CPU and Radeon+CPU both passed one warmup and 20 serial combined requests through Omni at nearest-rank complete-request p50/p95 **23.62/23.88 s** and **16.35/17.20 s**, respectively, with no prefetch warnings. First measured WAVs matched the expected sentence using pinned local ASR; both paths passed in-flight abort with a zero resource ledger. Four sequential one-request controls using native versus WSL UNC weights associate UNC I/O with the older slowdown, but cache, run order and power were not controlled. The slow UNC profile remains valid for its storage path; the CPU/Radeon profiles are not a paired speedup experiment. An initial 21 GiB Radeon repeat was correctly refused at admission under temporarily low available RAM and preserved as failure evidence.

A separate [WSL CPU Spark GGUF Omni profile](evidence/spark_omni_wsl_cpu/README.md) ran the same pinned Q4_K_M artifact through a Linux CPU-only llama.cpp server and current Omni controller. It passed one warmup and 20/20 serial inventory requests at nearest-rank complete-request wall p50/p95 **7.82/7.97 s**, a public `AsyncOmni.generate` text request, explicit context refusal and in-flight cancellation cleanup with a 4 GiB host reservation. The Linux server omitted the Windows offload-count line; the stage now requires positive CPU tensor-buffer evidence for that log layout and rejects accelerator buffers. This is independent of the earlier WSL vLLM INT8 result and does not qualify incremental streaming or general text quality.

The [hosted Galaxy S24 Spark experiment](evidence/spark_s24_full_attention/README.md) moved one real full-attention decoder layer with a fixed 1,024-token cache shape to the phone NPU. Its W8A16 QDQ QNN DLC inference matched the earlier S25 NPU outputs exactly on one pinned dataset; 100 NPU-attributed component samples had nearest-rank p50/p95 **1.109/1.205 ms**. Separate local FP32 and quantized CPU runs measured the numerical change, with 1.351% hidden-state relative L2 from original FP32 source to S24 output and no task-quality tolerance. AI Hub Workbench runs components on hosted physical devices, not the stateful local Spark generation loop; this cell remains NOT E2E.

The same layer artifact then ran on hosted [Snapdragon X Elite CRD](evidence/spark_xelite_full_attention/README.md) and [SA8775P ADP](evidence/spark_sa8775_full_attention/README.md) NPUs, with exact same-fixture outputs as S24/S25 and 100-sample component p50/p95 **1.433/1.606 ms** and **1.837/2.079 ms**, respectively. On [RB3 Gen 2 / QCS6490](evidence/spark_rb3_full_attention/README.md), both the reused and exact-device-compiled W8A16 QNN DLCs failed at graph composition. An FP32 ONNX CPU layer passed with source-relative L2 below 9e-7; calibrated W8A8 ran on NPU but had 20.9% hidden-state relative L2 and is numerically unqualified. These are separate device components, not full-model deployment or cross-device speed comparisons.
