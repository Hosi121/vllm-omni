# Native Windows CPU + Radeon 890M Qwen3-TTS scoped whole-model path

The 0.6B CustomVoice model completed two named English **text-to-WAV** requests in [CrispASR v0.8.35](https://github.com/CrispStrobe/CrispASR/releases/tag/v0.8.35), outside Omni. This is a **joint CPU+iGPU result**: the talker and codec were routed to Radeon 890M Vulkan, while the iterative code predictor was explicitly pinned to CPU FP32. It is not an all-Radeon pass or a CPU+iGPU+NPU pass. The [DirectML route failed quality](../qwen_tts_radeon890m_directml/README.md). Neither route establishes Omni streaming or release qualification.

The host was Windows 11 build 26200 on Ryzen AI 9 HX 370 with Radeon 890M driver `32.0.22018.6001`; an RTX 5090 Laptop was also present. `GGML_VK_VISIBLE_DEVICES=1` exposed only the Radeon adapter, enumerated as `Vulkan0`; `-dev 1` selected the original physical adapter. The [first placement log](crisp_tts_radeon_cp_cpu_20260923.log) records `AMD Radeon(TM) 890M Graphics`, `using preferred GPU backend: Vulkan0`, `code_pred CPU-pinned (72 tensors, 432 MB, copy=f32)`, and `codec: GPU default - loading weights onto Vulkan0`. The [runtime's routing source](https://github.com/CrispStrobe/CrispASR/blob/v0.8.35/src/qwen3_tts.cpp) routes the talker off Vulkan unless `CRISPASR_QWEN3_TTS_VULKAN_NATIVE=1`; that override was set for the passing runs, and the CPU-talkback message was absent. This is placement evidence for the named runtime configuration, not a per-operator profiler trace.

The runtime ZIP `crispasr-windows-x86_64-vulkan.zip` is 36,826,421 bytes, SHA256 `8c4f6483d3dad9ab4066f3853b48306e16e5b4010d1bf42054c81bf439166b3f`; its embedded build reports git `00c9e752` and CPU/Vulkan backends. The talker is the [Q8_0 GGUF conversion](https://huggingface.co/cstr/qwen3-tts-0.6b-customvoice-GGUF/tree/29094dcb46f19b0898616aa9aeb876aa9aa6e086), revision `29094dcb46f19b0898616aa9aeb876aa9aa6e086`, file SHA256 `5227dcbc4df7c5533341d111cc469fa491a48e722b23dd10f553181b52dff2d9` (967,980,192 bytes). The codec is the [F16 tokenizer GGUF](https://huggingface.co/cstr/qwen3-tts-tokenizer-12hz-GGUF/tree/344e279551177654762e5c7d39e217834325f222), revision `344e279551177654762e5c7d39e217834325f222`, SHA256 `70dc95dbfdd9aa5d9d406236ff771d061bf17b0cda02a72513953355606e719b` (358,453,280 bytes). The loader logged a 28-layer/1024-hidden talker, five-layer code predictor, 16 codebooks and 24 kHz mono output. These are quantized/converter artifacts, distinct from the original HF safetensors in the [CPU PyTorch record](../qwen_tts_native_cpu/README.md). The converter's source-checkpoint revision, calibration details and same-checkpoint numerical parity are not established by this record; the two ASR cases are only scoped task checks. Weights and binaries are local, not committed.

The server process was already loaded before the measured profile. Its 0.25 s samples during the profile observed at most 3,266,732,032 bytes working set and 4,398,071,808 bytes private, with host available RAM at least 26,836,635,648 bytes. These are **not** loading peaks, model-only unique RAM, or iGPU allocation measurements. The 20 measured requests used one repeated prompt at concurrency one; no playback stream, cancellation, broader speech-quality suite, concurrent admission, power mode or 30-minute thermal run was checked. Whisper tiny.en is an intelligibility proxy, not a perceptual or speaker-fidelity score. The measured RTF exceeds 1, so this does not meet M2's real-time playback gate.

The safe default Vulkan CLI [fell back to CPU for the talker and codec](crisp_tts_radeon_20260923.log); its 7.20 s output must not be counted as a Radeon result. Forcing all Qwen TTS stages onto Vulkan with the [native override](crisp_tts_radeon_native_20260923.log) hit the 360-frame runaway cap without EOS, and [disabling flash attention](crisp_tts_radeon_no_fa_20260923.log) did not repair it; both output WAVs are retained but the runtime explicitly says to discard them. Pinning the code predictor to CPU FP32 yielded the two named passing outputs above. A separate [flash-attention-on diagnostic](crisp_tts_radeon_cp_cpu_fa_20260923.log) produced PCM identical to the first passing no-flash run, so the CPU predictor pin, not the flash-attention setting, was the decisive change in this case. General numerical parity and task quality remain unproven. The result should be integrated only as a bounded whole-session stage with explicit hybrid placement and memory admission, then compared with CPU and other backends on matched output and power conditions.

Reproduce the first named CLI request in PowerShell after verifying the binary and GGUF hashes:

```powershell
$env:GGML_VK_VISIBLE_DEVICES = '1'
$env:CRISPASR_QWEN3_TTS_VULKAN_NATIVE = '1'
$env:CRISPASR_QWEN3_TTS_CP_BACKEND = 'cpu-f32'
$bin = 'C:\Users\zhout\w2\crispasr-v0.8.35-vulkan\crispasr-windows-x86_64-vulkan\crispasr.exe'
$dir = 'C:\Users\zhout\w2\models\crisp_qwen3tts_0.6b'
& $bin --gpu-backend vulkan -dev 1 --no-flash-attn --verbose `
  --backend qwen3-tts-customvoice `
  -m "$dir\qwen3-tts-12hz-0.6b-customvoice-q8_0.gguf" `
  --codec-model "$dir\qwen3-tts-tokenizer-12hz.gguf" `
  --voice ryan --tts 'Hello from the local computer.' `
  --tts-output 'C:\Users\zhout\w2\qwen_joint.wav' -n 96 --seed 42
```

For the resident profile, launch the same binary with `--server --host 127.0.0.1 --port 18175` in place of `--tts`/`--tts-output`, retaining the same environment and `--voice ryan`. Then run [profile_crisp_tts_http.py](../../../../experiments/profile_crisp_tts_http.py) with `--server-pid`, `--warmups 1`, `--repeats 20`, `--output-report` and `--output-wav`. The server uses its startup Ryan voice when the HTTP body omits `voice`; the log confirms the selected speaker. The server also auto-loaded an unrelated punctuation component during startup, before timing; this did not enter measured request wall time. Stop the server after profiling.
