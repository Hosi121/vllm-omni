# Spark-X2.5 GGUF through Omni on WSL CPU

The pinned Spark-X2.5-1.7B Q4_K_M GGUF now completes bounded text requests through Omni `StageRuntime`/`StagePool` on WSL CPU. A separate public `AsyncOmni.generate` request passed. This adds an admitted current-Omni GGUF path to the WSL CPU matrix cell; it does not replace the older vLLM INT8 profile or qualify broad text quality, incremental token streaming or post-cancel restart.

Host: Ryzen AI 9 HX 370, Ubuntu 26.04 on WSL2 kernel `6.18.33.2-microsoft-standard-WSL2`. The RTX 5090 Laptop GPU was not selected; `CUDA_VISIBLE_DEVICES` was empty and llama.cpp used `-dev none -ngl 0`. The installed controller packages were vLLM `0.29.0` and Omni `0.29.0rc2.dev71+g00510ce38.d20260922`. The executed Linux CPU-only llama.cpp server reported build `10849`, commit `e71b80510`, and SHA256 `0d6bb6ade8da8f3231917ce23261da5331333df0007dc4bda74c00e0774e092c`. The [model](https://huggingface.co/XHToken/Spark-X2.5-1.7B-GGUF/tree/1f7fa33b1245c14730da39e125714ad3a327901b) revision was `1f7fa33b1245c14730da39e125714ad3a327901b`, file `Spark-X2.5-1.7B-Q4_K_M.gguf`, SHA256 `902bde2522394954ac17821b3e5fd0df02defbc6944f122253f2580acf0503f4`. Model and executable remain outside Git; the stage verified both hashes before loading.

The Linux CPU-only build omits the Windows llama.cpp `0/29 layers offloaded` log line. The first [attempt](placement_parser_refusal.json) therefore failed closed during Omni placement verification even though the [server log](placement_parser_refusal_server.log) showed only CPU buffers. The verifier now accepts this layout only when the server explicitly reports no usable GPU, records one or more `CPU*` model tensor buffers, records no accelerator model buffer or accelerator layer assignment, and was launched with `-dev none -ngl 0`. The successful [profile server log](profile20_server.log) identifies `CPU_Mapped` and `CPU_REPACK` model buffers, a CPU compute buffer and a CPU-only device list. The [profile plan](profile20_report.json) records `cpu_only_layout=true`, `offloaded_layers=null`, loaded worker RSS 1.91 GB, a 4 GiB host-RAM reservation and a one-slot server. This fixes an evidence-format mismatch without treating missing GPU data as CPU proof.

A post-change [native Windows CPU regression request](windows_cpu_parser_regression_report.json) also passed the two named prompts with the earlier b11124 executable. Its [server log](windows_cpu_parser_regression_server.log) retained the `0/29` offload line and CPU buffers; the plan recorded `cpu_only_layout=false`. This one-request check tests the alternate log layout, not Windows performance.

The profile used a 4,096-token context, 96-token generation cap, temperature zero, no prompt cache and serial concurrency one. Both named requests passed: `Paris` for the short question and `1511` for district 73 of the synthetic 120-item inventory. After one warmup, **20/20** measured inventory requests were correct; nearest-rank complete-request wall p50/p95 was **7.82/7.97 s** (range 7.71–8.01 s), excluding 1.61 s stage startup. The server reported 2,463 prompt and 5 completion tokens for the measured request. The prompt was checked before submission; an over-context request was refused without truncation and a following short request passed. In-flight cancellation terminated the worker, emitted no stale output and released the ledger without quarantine. The [public entrypoint report](public_report.json) separately returned `Paris` and a terminal text event using the real Spark HF config directory for pipeline resolution while executing the pinned GGUF. The two OS builds have different llama.cpp commits and environments, so these timings are not a paired WSL-versus-Windows comparison.

The reservation includes the 1.11 GB GGUF and a declared 2 GiB for KV/workspace/transfer/headroom; loaded RSS is a snapshot, not a loading peak. Power and thermal conditions were not sampled. The backend returns one complete text response and retires the worker on a live-request cancellation. Broader reference-quality prompts, long contexts, incremental streaming, restart after cancellation, concurrent admission and sustained power/thermal measurements remain open.
