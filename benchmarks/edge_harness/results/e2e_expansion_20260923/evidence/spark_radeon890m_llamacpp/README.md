# Spark-X2.5-1.7B Q4_K_M on native Windows CPU and Radeon 890M

This is a **scoped, complete text-model path in standalone llama.cpp**, with real weights, prefill, autoregressive decode, KV state and answer delivery. It is **not** yet an Omni `StageRuntime` backend, and it says nothing about other Spark variants or the TTS/MiniCPM/VLA cells. The current [device × model matrix](../../../e2e_profiling_20260922/evidence/summary/README.md) distinguishes this backend result from Omni integration.

The GGUF is [XHToken/Spark-X2.5-1.7B-GGUF](https://huggingface.co/XHToken/Spark-X2.5-1.7B-GGUF/tree/1f7fa33b1245c14730da39e125714ad3a327901b) revision `1f7fa33b1245c14730da39e125714ad3a327901b`, file `Spark-X2.5-1.7B-Q4_K_M.gguf` (1,107,457,856 bytes; SHA-256 `902bde2522394954ac17821b3e5fd0df02defbc6944f122253f2580acf0503f4`). It remains in local model storage, not Git. The Windows Vulkan binary is [llama.cpp b11124](https://github.com/ggml-org/llama.cpp/releases/tag/b11124), build commit `1a679828f`; the release ZIP SHA-256 is `ece009eff2a18884246b4aef785ce4efd9eb36f4fc38e3d6727af6fe53bd2c75`. See the [artifact manifest](artifact_manifest.json) and [Vulkan enumeration](vulkaninfo_summary.log). The host was Windows 11 build 26200 on Ryzen AI 9 HX 370 with Radeon 890M driver `25.20.18.06 (LLPC)`. An RTX 5090 Laptop GPU was present, so the Radeon command explicitly selected `-dev Vulkan1`; the [placement log](spark_igpu_q4km_placement_20260923.log) records all 29 logged layer assignments on Vulkan1, a 1,051 MiB Vulkan1 model buffer and a separate 210 MiB Vulkan_Host buffer. The CPU command used `-dev none -ngl 0`. Both used a 4,096-token context, one slot, temperature zero, reasoning off for server requests, and default f16 KV cache.

Both backends returned `Paris` for the short question and `1511` for the 120-item inventory (district 73), with `finish_reason=stop`. The inventory generated by the profile script used 2,463 prompt tokens and five completion tokens. The [Radeon profile](spark_igpu_server_inventory_profile20_nocache_20260923.json) and [native CPU profile](spark_cpu_server_inventory_profile20_nocache_20260923.json) each contain the two quality checks, one excluded warmup, and all 20 measured serial HTTP request wall times. `cache_prompt=false` was sent and every measured response reported zero cached prompt tokens. Nearest-rank timings are:

| Full text request, 120-item inventory | Radeon 890M Vulkan1 | Native Windows CPU |
|---|---:|---:|
| p50 request wall | 2.18 s | 6.65 s |
| p95 request wall | 2.20 s | 6.86 s |
| Correct measured responses | 20/20 | 20/20 |

The [Radeon cancellation check](spark_igpu_server_cancel_20260923.json) and CPU profile each closed a live stream after its first content delta, then submitted a new question that correctly returned `Paris`. This checks subsequent request recovery; it does not prove the exact point at which llama.cpp stopped backend compute. A [single post-profile process snapshot](process_snapshot.json) records working sets of 1.84 GB for Radeon and 2.14 GB for CPU. These are neither peaks nor complete iGPU memory attribution.

The [three-repetition synthetic llama-bench](spark_igpu_q4km_bench_20260923.json) at p128/n32 recorded mean prompt throughput 1,602 tok/s and generation throughput 67.34 tok/s on Vulkan1; the [same-artifact CPU bench](spark_cpu_q4km_bench_20260923.json) recorded 402.22 and 54.61 tok/s. These are separate kernel-oriented measurements, not the complete-request times above. Their logs and the [one-repetition verbose placement check](spark_igpu_q4km_placement_20260923.log) are retained.

Two unsuccessful CLI attempts are retained: [context 2,048 refused](spark_igpu_inventory_answer_20260923.log) because the prompt needed 2,463 tokens, and [context 4,096 with reasoning enabled](spark_igpu_inventory_answer_ctx4096_20260923.log) exhausted a 256-token output limit before giving a final answer. The [reasoning-off 4,096-token run](spark_igpu_inventory_answer_no_reason_20260923.log) returned `1511`. The short reasoning-enabled [CLI run](spark_igpu_q4km_answer_20260923.log) returned `Paris`. These are workload/configuration boundaries, not general model failures.

To reproduce on this Windows host, download the pinned GGUF, verify its SHA-256, and use the pinned llama.cpp Vulkan release. Start one backend at a time with the full model resident:

```powershell
$bin = 'C:\Users\zhout\w2\llama-vulkan-b11124\bin'
$model = 'C:\Users\zhout\w2\models\Spark-X2.5-1.7B-Q4_K_M.gguf'
& "$bin\llama-server.exe" -m $model -dev Vulkan1 -ngl 99 -c 4096 -np 1 --host 127.0.0.1 --port 18173 --reasoning off --no-webui
```

Run [the profile script](../../../../experiments/profile_llamacpp_spark_text.py) in another terminal with `--model-file $model`, `--expected-model-sha256 902bde2522394954ac17821b3e5fd0df02defbc6944f122253f2580acf0503f4`, `--profile-case inventory_120`, `--cancel-check`, and an `--output` path. For CPU, launch the same binary with `-dev none -ngl 0` on another port and set `--endpoint` accordingly. The fixed artifact, context, precision, prompt and cache policy are required for comparison.

The next project gate is to wrap this **whole autoregressive session** as a bounded llama.cpp stage behind Omni's request/event, memory-admission, state, streaming and cancellation contracts, then compare it with the current vLLM CPU/CUDA paths. The two-answer quality check, one repeated input, absent load-peak/power/thermal data, and client-close-only cancellation check do not establish broader release qualification.
