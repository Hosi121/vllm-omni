# MiniCPM-o native Windows model-storage comparison

The native Windows MiniCPM-o GGUF Omni path completes the combined synthetic spoken-question + JPEG to text + speech workload with the model weights on local NTFS. A four-run sequential storage comparison associates the earlier severe slowdown with loading those weights through the WSL UNC path. It does not isolate causality: OS file cache, thermal state, and run order were not controlled. The original slow UNC results remain valid for that deployment path.

The ten source GGUF artifacts (8,872,306,371 bytes total) were copied without conversion from `/home/zhout/project/edge_infer/models/MiniCPM-o-4_5-gguf` to `C:\Users\zhout\w2\minicpmo_local_gguf`. The [comparison summary](io_comparison.json) covers four requests; the individual JSON reports pin the revision `db25077c33951fe163b42986fba0132e279872a2`, all ten artifact SHA256 hashes, the CPU or Radeon CLI SHA256, input hashes, a 21 GiB explicit shared-RAM capacity/demand, actual placement, terminal event, output and zero shutdown ledger. The same fixture and CLI were used within each storage pair. Each condition started a new Omni controller and executed one C++ model session.

The host was an AMD Ryzen AI 9 HX 370 laptop running Windows 11 build 26200 with Radeon 890M graphics driver `32.0.22018.6001`; the Windows controller environment had installed vLLM `0.29.0+cu134` and vLLM-Omni `0.29.0`. The whole-session model used the pinned Q4_K_M language and F16 auxiliary GGUF artifacts through the separately SHA-pinned native CPU/Vulkan CLI builds. The input was a 448×448 synthetic JPEG and 3.084 s, 16 kHz spoken question, with a 2,048-token context, at most 96 new tokens, serial concurrency one and a fresh C++ worker per request. Timing includes the complete request, worker loading and handoff but excludes controller startup; power and thermal conditions were not captured. This is not a GPU-only graph: Token2Wav remained on CPU.

All four requests answered “The square in the image is red.” and produced complete nonzero 24 kHz WAV files. The CPU native-weight route additionally passed [one warmup plus 20 serial measured complete requests](cpu_native_profile20.json): nearest-rank wall p50/p95 **23.62/23.88 s**, 20/20 correct texts and nonzero 1.60–2.88 s WAVs, no prefetch warning in [22 worker logs](cpu_native_profile20_worker_logs/), and no stale output or resource reservation after in-flight abort. Controller startup was 9.23 s, excluded from those request times; maximum sampled worker RSS was 13.10 GB. The first measured [WAV](cpu_native_profile20.wav) exactly matched the expected sentence using pinned Whisper tiny.en ([ASR proxy](cpu_native_profile20_asr.json), WER 0).

The Radeon+CPU native-weight route also passed [one warmup plus 20 serial measured requests](radeon_native_profile20.json): nearest-rank wall p50/p95 **16.35/17.20 s**, 20/20 expected texts and nonzero 2.08–2.88 s WAVs, no prefetch warning in [22 worker logs](radeon_native_profile20_worker_logs/), and no stale output or reservation after abort. All 21 successful worker logs identify Radeon 890M Vulkan0 language (37/37 layers) and vision, with CPU Token2Wav; the abort log does not establish a successful placement. Controller startup was 8.75 s, excluded from request times; maximum sampled worker RSS was 15.30 GB. The first measured [WAV](radeon_native_profile20.wav) exactly matched the sentence using [pinned ASR](radeon_native_profile20_asr.json), WER 0. These two one-output ASR results are only speech-intelligibility proxies. The CPU and Radeon runs were sequential, not randomized or thermal/power-matched, so their latency values do not establish an iGPU speedup.

An initial Radeon repeat was correctly [refused](radeon_native_profile20_refusal.json) before model load when the 21 GiB shared-RAM reservation no longer fit available memory after controller startup. The original [driver trace](radeon_native_profile20_refusal_driver.log) is retained. After reclaiming file cache, the identical 21 GiB configuration admitted and completed the profile above; this is evidence of explicit admission behavior, not an invitation to overcommit memory.

The four one-request [CPU-native](cpu_native.json), [CPU-UNC](cpu_unc.json), [Radeon-native](radeon_native.json), and [Radeon-UNC](radeon_unc.json) reports have companion driver and copied worker logs in this directory. The earlier [UNC Radeon 20-request profile](../minicpmo_omni_radeon_profile20/README.md) remains the measured result for that storage path: p50/p95 87.27/91.45 s and prefetch warnings on each worker. Local NTFS is a supported deployment choice here, but no general placement speedup is inferred from comparing the separate CPU and Radeon samples. The synthetic fixture does not establish general image/audio quality, playable streaming, concurrency, loading-peak admission or sustained power/thermal behavior.

The checked-in Windows log copies have line endings and trailing whitespace normalized for review; the native worker-log directories remain under `C:\Users\zhout\w2\minicpmo_io_{cpu,radeon}_native_profile20_logs`. The JSON reports are the primary timing records, and the source GGUF weights remain outside Git.

To reproduce, use [`probe_omni_minicpmo_cpp.py`](../../../../experiments/probe_omni_minicpmo_cpp.py) with the pinned fixtures and artifact report in [`minicpmo_cpp_radeon890m_prompted`](../minicpmo_cpp_radeon890m_prompted/), `--model-dir C:\Users\zhout\w2\minicpmo_local_gguf`, an exact pinned CLI executable/hash, `--capacity-gib 21 --reserve-gib 21`, and `--warmups 1 --repeats 20 --abort-check`. The [older Radeon profile README](../minicpmo_omni_radeon_profile20/README.md) contains the complete PowerShell invocation; change only the model directory and output paths for this test. Do not compare the native and UNC numbers as a randomized benchmark.
